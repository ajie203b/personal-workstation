# PR #9 审查

PR：<https://github.com/ajie203b/personal-workstation/pull/9>，标题“安卓 App 与 Windows 桌面版应用内自动更新”。

首次比较：base `5ff2a2c3ffeca9333f9c27d44b3fb81a8f13cdea` → head `2f2d3be55899280d52500e1f695e3cff3df6261c`。按实现规范/可靠性和 PR 正文需求两个独立角度审查。v3.4.0 不包含此 PR；后续按用户要求修复并纳入 v3.4.1。

## Standards

- **P2：在镜像下载成功前验证签名和目标版本。** `AppUpdatePlugin.java:310–318` 仅校验 APK 包名；同包名的错误签名或旧包会终止来源重试并返回成功，`appUpdateClient.ts:269–282` 又按目标版本缓存路径。系统安装器虽会拒绝错误签名，但重试持续使用坏缓存，后续镜像没有机会。应在下载来源循环内核对签名、版本，拒绝错误包并尝试下一来源；失败重试应能清除缓存。
- **P2：保护正在使用的桌面更新句柄。** `src/stores/appUpdate.ts:18–22` 的 `show()` 会释放旧句柄。启动延迟自动检查与用户手动检查可以并发；后到结果释放了正在下载的旧句柄，`appUpdateClient.ts:165–172` 随后安装可能失败。应合并检查请求，并在下载安装期间保护活动句柄。

## Spec

- **P2：关闭开关后仍可能自动检查。** 对应 PR 正文“可以在设置里关掉”。`src/shared/AppUpdate.tsx:27–34` 只在挂载时读取开关；用户在启动后 6 秒内关闭，已设定计时器仍会检查、展示弹窗。执行检查和展示前应再次核对设置。
- **P2：自动检查与手动更新竞态。** 对应“立即更新…失败时可以重试”。与 Standards 第二项是同一问题：后到的自动检查结果使正在下载安装的句柄失效。

PR 未承诺取消下载，因此未将缺少取消 API/UI 计为需求遗漏。Tauri 公钥占位、未配置密钥只出普通 EXE 的行为已在 PR 中明确说明，未当作隐藏缺陷。签名配置条件、标签生成 `latest.json` 及附件命名与当前发布脚本基本吻合；真实安装、授权和签名更新链路仍需平台验证。

Standards 2 项、Spec 2 项，去重后共 3 项；最主要的是错误安装包缓存与更新句柄竞态。

## 修复与复核

- 安卓 `verifyApk` 在每个下载来源完成时、每次安装前读取 APK 包信息，并通过独立 JVM 策略校验包名、目标版本、更高版本码和完整签名集合；不匹配则拒绝，下载循环继续尝试下一来源。系统安装器仍执行最终签名校验。使用当前签名，不自动接受证书轮换。
- 前端传递目标版本，安装失败后清除缓存记录，授权成功后复用的缓存仍要重新验证；进度监听在下载失败时释放。
- 重叠检查共享一个 Promise/结果；全局 busy 状态防止晚到结果释放当前安装句柄。复核时另发现设置页持有旧句柄的问题，增加真实 DOM 回归并改为只打开全局当前更新。
- 启动计时器执行前读取自动检查设置，结果返回后再次读取；丢弃的闲置句柄在其他等待者有机会接管后释放。关闭授权弹窗后停止自动继续安装的监听。
- 14 项更新器 JS 回归通过，原先自动开关、坏缓存、句柄生命周期故障均有 RED → GREEN 记录；8 项 JVM 身份规则测试通过，Android 原生代码编译通过。全套 612 项 Vitest 与生产构建通过。Windows 中文路径下 Gradle 单测执行器无法找到测试类，本机使用同一已编译类和 JUnitCore 执行；CI Linux 直接执行 `testDebugUnitTest`。

API 依据：[SigningInfo](https://developer.android.com/reference/android/content/pm/SigningInfo)、[PackageInfoCompat](https://developer.android.com/reference/androidx/core/content/pm/PackageInfoCompat)。未执行安卓真机安装或桌面签名自动安装；Tauri 公钥与 CI 私钥未配置时仍走手动下载。
