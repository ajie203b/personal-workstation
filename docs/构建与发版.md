# 构建与发版

这份文档讲「怎么把它做出来、怎么发出去」。功能与用法看 [../README.md](../README.md)。

## 环境要求

| 依赖 | 位置 / 版本 |
| --- | --- |
| JDK 21 | `%LOCALAPPDATA%\jdk-21`（Capacitor 8 要求；构建时把 `JAVA_HOME` 指过去） |
| Android SDK | platform 35 + build-tools 35.0.0，装在 `%LOCALAPPDATA%\Android\Sdk`；路径写在 `android/local.properties`（已 gitignore） |
| 中文项目路径 | `android/gradle.properties` 里已加 `android.overridePathCheck=true`，否则 AGP 拒绝构建 |
| Android Studio 用户 | `Settings → Build, Execution, Deployment → Build Tools → Gradle → Gradle JDK` 选 JDK 21 |

`JAVA_HOME` 必须写成 Windows 反斜杠形式。Git Bash 习惯写的 `/c/Users/...` 会被 JDK 启动器当非法路径，Gradle 报的却是「找不到签名配置」一层的错，很难往回猜。

## 本地开发

```bash
npm install
npm run dev        # http://localhost:5173
npm test           # vitest 单测：日期解析 / 自然语言录入 / 重复任务推算
npm run build      # 产出 dist/ + PWA（Service Worker 自动生成）
npm run preview    # 生产预览：http://localhost:4173
npm run preview:lan  # 局域网访问
```

## 发网页版

```bash
bash scripts/deploy-gh-pages.sh
```

脚本构建 `dist/` → 按 `package.json` 写 `version.json` → 只快进推送 `gh-pages`（远端分叉时停下报错，不覆盖历史）。只有纯文档/脚本改动、要复用已有 `dist/` 时才加 `--fast`；**代码改动时别用**，否则推上去的是旧产物。

`dist/` 只存在于 `gh-pages` 分支，main 不跟踪它（`.gitignore` 忽略 `dist`），所以构建产物的增删不会让 `git status` 变脏。

## 出 APK

```bash
npm run build            # 先构建 Web 资源
npx cap sync android     # 同步进安卓工程（web 资源变化后必须重新执行）
```

然后任选其一：

- **Android Studio**：打开 `android/` → `Build > Build App Bundle(s) / APK(s) > Build APK(s)`
- **命令行**：

  ```bash
  cd android
  ./gradlew assembleDebug      # app/build/outputs/apk/debug/app-debug.apk
  ./gradlew assembleRelease    # app/build/outputs/apk/release/app-release.apk（签名正式包）
  ```

## 一键完整发版（推荐）

在 Windows 的 PowerShell 7 中，先准备好版本号、更新记录，并将待发布代码提交推送到 main，然后运行：

```powershell
pwsh -ExecutionPolicy Bypass -File .\scripts\release.ps1 -Publish
```

需要 Git for Windows（含 Git Bash）、已登录的 GitHub CLI（`gh auth login`）、上述 Android 构建环境，以及已配置从 `gh-pages` 分支部署的 GitHub Pages。脚本会先检查本次标签和 Pages 地址，再构建、验签 APK，创建 Release，等待云端 EXE 构建并下载到 `apk/`。确认 Release 上有本次 APK 和 EXE 后，复用本次构建的 `dist/` 发布网页及 `version.json`，最后轮询线上版本，最多约三分钟。**线上版本与本次版本一致才显示“完成”。**

普通运行只出 APK；`-Exe` 额外构建下载 Windows 安装包；这两种模式不发布网页。`-SkipPull` 用于已确认源码的分支构建，会跳过切 main 和拉代码。发布只检查本次版本的本地、远端标签，不拉取或覆盖其他历史标签。

终端默认只显示关键进度，并保留依赖审计的 high/critical 汇总提示；每次运行的完整工具输出保存到 `apk/logs/release-*.log`，失败时会显示最后 12 行工具输出和日志位置。需要实时查看详细构建输出时，在原命令后加 `-Verbose`。

本地 APK 构建和验签完成后，脚本将检查点保存到 `apk/release-v<版本>.json`。后续网络、云端构建或 Pages 部署失败，保持同一提交和本地产物，运行：

```powershell
pwsh -ExecutionPolicy Bypass -File .\scripts\release.ps1 -Publish -Resume
```

续跑会跳过拉代码和本地构建，核对提交、版本、APK 与 `dist/` 的哈希，并检查远端标签、已有 APK 附件及桌面构建任务。缺少 Release 或 APK 附件时补建；失败的桌面任务会重试；已下载且哈希一致的 EXE 直接复用；已推送的网页只重新确认线上版本。不会覆盖已有标签或内容不同的 APK 附件。检查点只适用于这版脚本开始的发布，之前的发布没有检查点。

若在生成检查点前失败，直接重跑普通 `-Publish`。若源码或产物已经改变，请回到原提交并恢复原产物续跑，或给新代码升版本后重新发布。不要删除标签来重试已有版本。`apk/` 是本地构建和续跑缓存，发布结束前不要清理。

脚本的离线回归测试：`pwsh -File .\scripts\release.test.ps1`。测试替换外部工具和网络请求，不会真实构建、推标签或发布；CI 在 Windows 上自动执行。

Windows 工作流缓存 npm 下载内容，并在 main 的 Rust 依赖或工作流变化时构建一次、预热 Rust 缓存。GitHub 的不同标签不能互读各自的缓存，但可以读取默认分支缓存，因此 Rust 缓存在标签发版时只读，不再为每个标签保存一份副本。普通前端提交不额外触发桌面构建。首次预热仍需完整编译，实际提速取决于缓存命中和依赖变化；工具链更新后可在 Actions 中以 main 手动运行 `Desktop (Windows)` 刷新缓存。缓存权限与作用域依据 [GitHub 官方说明](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)。

## 手动完整发版链路

「检查更新」有两个数据源：主源是 Pages 上的 `version.json`（静态文件带 CORS，网页版与安卓壳内都能读，不吃 API 限流），GitHub Releases API 只在确有新版时用来取 APK 直链。所以只推 main 不推 Pages，两端都还以为自己是最新；只推 Pages 不发 Release，手机能收到「发现新版本」却拿不到新包。

应用功能或修复交付给用户时，需要网页与安装包一起发布。使用上面的一键脚本，或按以下步骤手动执行：

1. **升版本号**：`npm version <x.y.z> --no-git-tag-version`（一次改好 `package.json` 与 `package-lock.json`）；再手改 `android/app/build.gradle` 的 `versionCode`（**每发一版 +1**，Android 只认它判断能否覆盖安装）与 `versionName`（跟 npm 版本一致）。动手前先确认这一版不是空的：`git log --oneline origin/main..HEAD` 看有没有未发的提交，`gh api repos/ajie203b/personal-workstation/releases/latest --jq .tag_name` 对一下线上版本。
2. **提交并推送 main**：功能改动与版本号改动进同一个提交。
3. **发网页版**：见上一节。跑完自己核对一次 `curl -fsS https://ajie203b.github.io/personal-workstation/version.json`——Pages 重建有几十秒延迟，脚本末尾那次 curl 很可能仍打印旧值。
4. **出安卓包**：`cd android && JAVA_HOME="%LOCALAPPDATA%\jdk-21" ./gradlew assembleRelease`。
   - 增量构建约 20 秒，首次全量约 3.5 分钟。若 `gradlew` 报 `SocketTimeoutException: Connect timed out` 且栈顶是 `org.gradle.wrapper.Install.forceFetch`，那是 wrapper 在下 Gradle 发行版而不是项目坏了：本机 `GRADLE_USER_HOME=D:\gradle-home` 一旦被清空，就要重新下约 230MB 的 `gradle-8.11.1-all.zip`，而官方源只有约 250KB/s，撑不过 wrapper 写死的 10s 超时。处理办法是先把发行版预置进 `$GRADLE_USER_HOME/wrapper/dists/gradle-8.11.1-all/<hash>/gradle-8.11.1-all.zip`（删掉残留的 `.part` / `.lck`），国内镜像约 46MB/s，再**用官方 `gradle-8.11.1-all.zip.sha256` 校验一致**后重跑构建。别改仓库里的 `gradle-wrapper.properties`，也别反复重跑碰运气。
5. **验包**（构建成功不等于包是对的，三查缺一不可）：
   - `aapt2 dump badging app-release.apk | grep ^package` → versionCode / versionName 是新版；
   - `keytool -printcert -jarfile app-release.apk` 的 SHA256 指纹必须与上一版一致，不一致说明换了 keystore，已装设备只能卸载重装、数据会丢；
   - `unzip -p app-release.apk assets/public/assets/<本次改动的资源文件>` 确认改动真的进了包（对抗「sync 没生效 / 复用了旧 dist」这类静默失败）。

   然后复制成 `apk/personal-workstation-v<版本>.apk`，并更新本文档「本机当前产物」与 README 顶部版本行。
6. **发 Release**（提供手机安装包下载地址）：

   ```bash
   gh release create v<x.y.z> apk/personal-workstation-v<x.y.z>.apk \
     --title "v<x.y.z> · <一句话>" --notes "<改动清单 + 在线版链接>"
   ```

   资产名带版本号，App 内按接口返回的 `browser_download_url` 取下载地址，不拼死路径。

**收尾核对**：`version.json` = 新 tag = Release 资产存在且能下载，三处一致才算发完。

## 每日模型排名数据

`.github/workflows/intelligence.yml` 每天 05:17 UTC 更新两样东西，有变化就分别提交到 main：

1. `public/intelligence.json`：调 artificialanalysis.ai 的 `GET /api/v2/data/llms/models`，取智能指数前 30。
2. `public/intelligence/chart.png`：官网首屏智能指数图表的浏览器截图（Recharts 客户端渲染，没有稳定图片地址）。

- 数据链路：`scripts/fetch-intelligence.mjs` 优先用官方 API（需要仓库 **Settings → Secrets and variables → Actions** 里的 `AA_API_KEY`）；**没有这个 secret 时自动退到解析官方公开榜单页**（`https://artificialanalysis.ai/leaderboards/models` 里的 RSC payload），所以不再出现「工作流天天失败、榜单永远不更新」。两条路都只取智能指数、都取前 30，失败一律不覆盖旧文件并以非 0 退出。
- 图表链路：`scripts/fetch-intelligence-chart.mjs` 用 Playwright 打开官网首页，截取第一张宽 ≥1000 的 Recharts 大图，2x 输出并补白底；失败保留旧图并以非 0 退出。先用图表文本/分数/Logo/配色的 SHA-256 指纹对比 `scripts/intelligence-chart.json`，内容没变就不重截、不提交，避免抗锯齿噪声每天产生新 PNG。JSON 与图表分两次提交，图表截图失败不会阻断 JSON 更新。
- 手工跑一次：`node scripts/fetch-intelligence.mjs`（本地无 key 也能出 `public/intelligence.json`）、`CHROME_PATH="C:/Program Files/Google/Chrome/Application/chrome.exe" node scripts/fetch-intelligence-chart.mjs`，或 `gh workflow run intelligence.yml`。要跳过内容指纹强制重截图表，用 `gh workflow run intelligence.yml -f force_chart=true`。
- `src/lib/intelligence.ts` 保留结构化数据下载与缓存工具；当前工具页不调用它，也不把 JSON 的日期当作图片更新时间。
- 卡片展示的是**官方图表原图**；运行时优先拉 `main` 上的当日图表（带日期参数绕过缓存），加载成功后替换内置图，离线或远程失败回退 `public/intelligence/chart.png`。内置图仍在 PWA 预缓存里，支持横向滑动、鼠标拖动、键盘滚动、查看完整原图及打开官网。
- 内置图随版本更新，但每日 Action 会更新远程图：网页版、桌面版与安卓包**无需重新发版**，联网打开工具页即可看到最新官方图表。需要查看官网最新榜单时，使用卡片右上角的官网入口。

## 应用内自动更新（一次性配置）

### 当前配置（v3.4.2）

桌面更新公钥已写入客户端，两项 GitHub Actions Secret 已设置。v3.4.2 起发布 EXE、`.exe.sig` 与 `latest.json`；CI 和本机发布脚本均独立核验 Ed25519 文件签名、受信任版本字段及清单对应关系，校验不通过即停止。PR 不注入更新私钥。

旧版桌面客户端没有本次公钥，需要手动覆盖安装 v3.4.2 或更新版本一次；以后可应用内更新。这里的更新签名不等同于 Windows Authenticode 代码签名。

本机密钥目录为 `$env:USERPROFILE\.tauri\kairos-updater`，含加密私钥 `kairos.key`、公钥 `kairos.key.pub` 和口令保护文件 `password.dpapi`。不要将目录内容提交到仓库。DPAPI 口令文件只可由原 Windows 用户解密，**单独复制该文件到新电脑不能恢复口令**；迁移或重装前须在原电脑将私钥和口令另行备份到密码管理器。

`pwsh -NoProfile -File scripts/setup-updater-signing.ps1 -Upload` 可复用本机同一密钥更新两项 Secret，并先执行真实 Tauri 签名自检。脚本拒绝自动覆盖密钥或替换现有公钥；若本机缺少与已配置公钥匹配的私钥，请恢复原密钥，不要重新生成。

签名校验测试：`npm run test:scripts`；发布流程离线测试：`pwsh -File scripts/release.test.ps1`。协议依据：[Tauri Updater](https://v2.tauri.app/plugin/updater/)、[Minisign](https://jedisct1.github.io/minisign/)。

### 新项目手动配置参考

安卓 App 和 Windows 桌面版内置了自动更新：启动后静默检查（安卓每天最多一次，可在「设置 → 关于」关闭），有新版弹窗显示版本号和更新说明，一键下载安装。网页版（PWA）由 Service Worker 自己更新，不显示这些入口。

**安卓**无需额外配置：App 读 GitHub Releases 的最新版，下载 `personal-workstation-vX.Y.Z.apk`（GitHub 20 秒连不上自动换镜像），再拉起系统安装器。第一次更新时系统会要求允许 Kairos「安装未知应用」，App 会自动跳到对应设置页。

**桌面版**用 tauri-plugin-updater，下载的安装包必须带签名才会安装。下面的配置只需做一次（在自己电脑上）：

1. 生成更新签名密钥（会提示设置口令，记住它）：

   ```powershell
   npx tauri signer generate -w $env:USERPROFILE\.tauri\kairos.key
   ```

   生成 `kairos.key`（私钥）和 `kairos.key.pub`（公钥）两个文件。
2. 打开 `kairos.key.pub`，把里面**整串内容**填进 `src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`，替换占位符 `REPLACE_WITH_TAURI_UPDATER_PUBKEY`，提交到 main。
3. 打开仓库 **Settings → Secrets and variables → Actions → New repository secret**，添加两个 secret：
   - `TAURI_SIGNING_PRIVATE_KEY`：`kairos.key` 文件的**全部内容**；
   - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`：第 1 步设置的口令（没设口令就填空或不建）。
4. 之后照常 `scripts/release.ps1 -Publish` 发版：`desktop.yml` 在 v* 标签构建时会额外生成 `Kairos_X.Y.Z_x64-setup.exe.sig` 和 `latest.json`（版本号、CHANGELOG 对应段、安装包地址与签名），一起挂到 Release。客户端从 `releases/latest/download/latest.json` 读取。

说明与注意：

- 没配置密钥（或公钥还是占位符）时，桌面构建照常只出 exe，不会失败；桌面版里「检查更新」会提示去发布页手动下载。
- **配置之前发布的桌面版本里公钥是占位符，无法自动更新**：配好后需要手动装一次新版，之后才能自动更新。
- ⚠️ **私钥和口令务必备份**（例如存到密码管理器）。私钥丢失后只能换新密钥，已安装的旧版本因为公钥对不上，**再也无法自动更新**，只能手动下载安装一次新版。
- ⚠️ 安卓 APK 必须一直用**同一个 keystore 签名**（见下方「签名密钥与口令」），否则系统安装器会拒绝覆盖安装，自动更新也就失效。
- latest.json 只在发版标签上生成；手动运行 / PR 构建只出 exe（配了密钥时会多一个 .sig）。

## 签名密钥与口令

- keystore：`android/app/workstation.keystore`，口令写在**本机** `android/keystore.properties`。两个文件都已 gitignore，`build.gradle` 运行时读取，缺文件直接报错而不是回退到明文。
- **换手机重装、后续升级都用同一个 keystore 签名**，否则需要先卸载旧版（会丢数据，记得先在设置里导出备份）。装 debug 包后再装 release 包报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` 也是同一原因。
- ⚠️ 这个仓库曾长期私有，现已公开，而 git 历史里带着旧签名口令。请把它当**已泄露**处理：要真正收紧就得生成新 keystore，并让已安装设备卸载重装（同签名覆盖升级会失效）。口令不再出现在当前代码里，但历史不改写。
- 换电脑构建前请先备份这两个文件——丢失后无法对已安装设备覆盖升级。
